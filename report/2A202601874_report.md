## 1. Defense Summary

- Input guardrails block direct injection, Unicode-obfuscated injection, and extraction prompts that try to recover secrets.
- Output guardrails redact secrets and fail closed when a response contains API keys, passwords, phone numbers, or internal hosts.
- HITL escalates high-risk actions such as transfers, profile changes, and policy conflicts instead of auto-sending them.
- Egress policy allows only exact VinBank HTTPS destinations and rejects sensitive payloads before any data leaves the agent.
- The offline fallback used for lab execution keeps the demo deterministic, but the policy logic is still exercised end-to-end.

## 2. Layer Analysis

- `input_guardrail` is the first hard stop for jailbreaks, fill-in-the-blank attacks, translation attacks, and Vietnamese prompt injection.
- `output_guardrail` is the last content filter before user-visible output and catches API keys, passwords, phone numbers, and email addresses.
- `rate_limiter` blocks bursts after 10 requests in the lab suite, which is visible in `outputs/results.json` as `passed: 10` and `blocked: 5`.
- `hitl` escalates `transfer_money` and account/profile changes so the model does not become the final authority on risky actions.
- `assignment.pipeline.is_egress_allowed()` enforces an exact-domain allowlist and fails closed on sensitive payloads.

## 4. False Positives / Trade-offs

- Very strict filters can over-block borderline support requests that mention contact details, profile updates, or administrative terms.
- One trade-off visible in the lab is that a user asking to update a phone number can receive a generic banking redirect instead of a detailed workflow.
- The policy intentionally prefers safety over permissiveness for the lab, especially when a prompt mentions secrets, internal systems, or override language.

## 5. Gap Analysis

- No heuristic defense is perfect, and the lab uses deterministic fallbacks for repeatable grading.
- A production system would still need provenance tracking, stronger retrieval controls, and policy enforcement at the tool boundary.
- NeMo is wired in as an additional layer, but it is still a secondary safety net rather than the only defense.
- The bonus path on the Guards Agent was not achieved in this run, which is the correct outcome for a strong defensive baseline.

## 6. Production Readiness

- Centralize policy checks so the allowlist, redaction logic, and HITL escalation are not spread across multiple ad hoc call sites.
- Store API keys in a secret manager and rotate them when they appear in logs, screenshots, or paste buffers.
- Keep request IDs across input, model output, audit logs, and metrics so incident response can replay the exact path.
- Add alerts for block rate spikes, rate-limit hits, and judge failures so a sudden attack burst is visible quickly.
- For user experience, keep the strict safety rails but add more nuanced allow rules for legitimate banking tasks that mention profile data.

## 7. Ethics

- There is no perfect safety guarantee, so the right goal is controlled risk reduction, not absolute security theater.
- Safety controls should reduce exposure while preserving ordinary banking tasks for legitimate users.
- Human review is essential for high-risk decisions because the model should not become the final authority on money movement or identity changes.
- The lab also shows a responsible testing pattern: attack the unsafe target for learning, and only use the hardened target as a bonus challenge.
